# Implement Tasks

Use this skill explicitly from the primary Git checkout inside a **Herdr GUI** session (`HC_TERMINAL_ID`, via `herdr-app` + `hc`) or a **Herdr TUI** session (`HERDR_ENV=1`, via `herdr`) from any supported coding-agent harness pane. Move eligible tasks to **To Do** in `Backlog.md`, then invoke `implement-tasks` (with optional task IDs, harness pool hints, subscription-limit preferences, `--handle`, `--no-review`, `--pr`, or `--local`).

Three orthogonal mode axes control delivery, integration, and review:

- **Delivery modes:**
  - **Local merge (`local`, default unless configured otherwise):** Branches from the primary checkout, integrates via local `git merge --no-ff --no-commit`, and never runs `git push` automatically.
  - **GitHub Pull Request (`pr`, enabled via `--pr` or `## Delivery Mode` = `pr` in `.agents/implement-tasks-auto-merge.md`):** Branches each task worktree cleanly from `origin/<primary_branch>` (`base_sha`) without uncommitted/unpushed `Backlog.md` card commits inside `<task_branch>` so parallel PRs never conflict on tracker files. During coding and peer review, `git push` remains forbidden. Only **after** the Review Gate completes (`verdict=pass`, or verified `ready` when review was skipped), the Runner sends a `$ship_token` handoff to the **Worker** in `<worktree_path>`, authorizing `git push -u origin HEAD:<task_branch>` and opening/updating a GitHub PR (`gh pr create --base <primary_branch> --head <task_branch>`) formatted with `.agents/skills/pr/SKILL.md` (when present) and `GLOSSARY.md` vocabulary. The Runner watches CI checks (`gh pr checks <pr-url> --watch`), routes any failed run logs (`gh run view --log-failed`) back to the Worker (and Reviewer for non-trivial code fixes within the 5-round cap), and once CI is green either merges via `gh pr merge` + `git pull --ff-only` + `Backlog.md` `Done` commit/push (when `approval=auto` and not `--handle`) or opens `summary-<task-id>` with the PR link and CI summary awaiting `approve <task-id>`.
- **Integration modes:**
  - **Default (risk-gated auto-merge):** Routine, verified changes (`pass`, or review-skipped via the Review Gate, plus green PR checks in `pr` mode) that satisfy the project's `.agents/implement-tasks-auto-merge.md` rules and carry `approval=auto` are archived, merged (`--no-ff --no-commit` in `local` mode or `gh pr merge` in `pr` mode), committed as `Done` in `Backlog.md`, and automatically cleaned up (Herdr terminals, space/workspace, Git worktree, merged branch), advancing `base_sha` and updating the Runner's **Status Pane** with links to archived evidence. Complex, risky, sensitive-path, or unverified changes (or runs with unconfigured rules) pause and wait for your explicit `approve <task-id>`. In `local` mode, `git push` always requires separate explicit authorization.
  - **Manual approval (`--handle`):** Disables auto-merge for every task. All completed tasks remain **In Progress** with their worktree, Worker, Reviewer (if launched), PR (in `pr` mode), and task-tab **Summary Pane** open until you explicitly authorize `approve <task-id>` (or synonym `merge <task-id>`).
- **Review modes (orthogonal to `--handle` and `--pr`/`--local`):**
  - **Default (peer-to-peer review with trivial-task skip):** Evaluates a post-diff **Review Gate** after Worker completion: truly trivial mechanical diffs that satisfy the built-in baseline (and any optional `## Skip Review (Trivial Tasks)` rules in `.agents/implement-tasks-auto-merge.md`) skip launching a Reviewer and proceed directly to PR publishing (in `pr` mode) or archiving and the Approval Gate (this still applies under `--handle`); all other tasks run independent peer-to-peer review.
  - **No-review mode (`--no-review`):** Skips launching Reviewers for all tasks in the run. The Runner still inspects each verified Worker diff, checks verification gaps, and enforces `.agents/implement-tasks-auto-merge.md` (including startup onboarding when not running with `--handle`) and the Approval Gate alone (routine verified tasks auto-merge after passing CI in `pr` mode; risky, sensitive, high-risk, or unverified tasks pause for `approve <task-id>`; combine `--no-review --handle` to skip review and pause every task for manual `approve`).

## Select and assign

1. Detect the Orchestration Backend:
   - **Herdr GUI (primary):** when `HC_TERMINAL_ID` is set, read `herdr-app --skill` and `hc --skill` and verify `herdr-app ls` and `hc ls --json`. Never fall back to `herdr` TUI commands inside Herdr GUI.
   - **Herdr TUI (fallback):** when `HC_TERMINAL_ID` is unset and `HERDR_ENV=1`, read `herdr --skill` (or the `herdr` skill) and confirm installed `herdr` commands.
   Identify the primary checkout (`git rev-parse --show-toplevel`), its current branch, and `<git-common-dir>`, ensuring `.implement-tasks/` is listed in `<git-common-dir>/info/exclude` without modifying the repository's tracked `.gitignore`. Follow [Herdr dispatch](references/herdr-dispatch.md), [harness routing](references/harnesses.md), and [auto-merge rules](references/auto-merge-rules.md).
2. Check project auto-merge and delivery configuration:
   - Inspect `<repo-root>/.agents/implement-tasks-auto-merge.md` (or a custom path declared in `AGENTS.md`/`CLAUDE.md`) per [auto-merge rules](references/auto-merge-rules.md), resolving `delivery_mode` (`local` default, overridden by `## Delivery Mode` or explicit `--pr` / `--local` launch flags).
   - When not running with `--handle`, if the file is missing or unfilled, **warn the user** and ask whether to: (a) let the Runner analyze the project and draft `.agents/implement-tasks-auto-merge.md` for confirmation, (b) record rules dictated by the user, or (c) continue this run safely requiring `approve <task-id>` for all tasks (never silently auto-merge without configured rules).
3. Reconcile existing Run Records in `<git-common-dir>/implement-tasks/` first so in-flight `In Progress` runs are resumed by task ID and phase. Then query newly eligible tasks from the Task Source (`Backlog.md`) via `backlog task list --status "To Do" --ready --json` and compare against `backlog task list --status "To Do" --json` (without `--ready`) to detect blocked dependencies. Apply any explicit task-ID filter (an explicitly named `Backlog` task is eligible). Keep blocked dependencies, parent grouping tickets, tasks assigned to someone else, and owner-only tasks per `AGENTS.md`/`CLAUDE.md` (for example `project: owner`) out of the execution queue. Report skipped and deferred tasks with reasons. Keep tracker mutations isolated to the Runner so alternative Task Sources can be added later without changing the core loop. If no eligible or resumable tasks remain, finish without launching agents or panes.
4. Once at least one eligible or resumable task is identified, open (or reuse) the Runner's **Status Pane** (`implement-tasks-status`) beside the Runner pane and render `<git-common-dir>/implement-tasks/status.md` per [Herdr dispatch](references/herdr-dispatch.md#runner-status-pane-statusmd); refresh it on every queue or task transition. Run up to **10 independent tasks** concurrently across implementation and review by default (worktrees awaiting `approve` free a concurrency slot). Read project-specific conflict surfaces, exclusive local-resource serialization rules (for example, shared IDE/editor instances, databases, ports, or test hardware), and verification/artifact expectations from `AGENTS.md`, `CLAUDE.md`, and the launch prompt. Defer tasks likely to conflict with pending edits to shared files until those edits are integrated, and serialize checks that contend on an exclusive local resource. Reassess the queue as tasks finish or merge.
5. When dispatching a `To Do` task for the first time:
   - Verify the task card file is clean and committed in the primary checkout (`git status --porcelain -- <card-path>`).
   - Update the task via `backlog task edit <task-id> --status "In Progress"` (and set assignee `-a <worker-name>` if unassigned, respecting any existing human assignment), then commit **only** that card file in the primary checkout (`git commit --only -m "<task-id>: In Progress" -- "<card-path>"`).
   - In `local` mode, pin `base_sha` to the resulting `HEAD`. In `pr` delivery mode, fetch `origin` (`git -C "$repo_root" fetch origin "$primary_branch"`) and pin `base_sha` to `origin/<primary_branch>` (`git rev-parse "origin/$primary_branch"`) so unpushed `Backlog.md` card commits stay out of `<task_branch>` and parallel PRs never conflict on tracker files. Create the task branch and linked worktree from `base_sha`, and launch the Worker in the new Herdr GUI space (`herdr-app do space.new`) or Herdr TUI workspace (`herdr worktree create`).
   - If worktree creation or Worker startup fails before prompt delivery, roll the card status back to `To Do` in the primary checkout and commit the rollback.
   - Keep all `Backlog.md` mutations with the Runner. Pass the Worker the task ID, acceptance criteria, relevant specification and absolute paths from the primary checkout (uncommitted tracker files are absent in a fresh worktree), applicable repo instructions and topic rules, and mandatory prompt guardrails.

## Implement, review, summarize, and integrate

- **Harness, model, and effort selection:** Select the harness, model, and reasoning effort separately for each Worker and Reviewer based on task complexity, card preferences in `AGENTS.md`/`CLAUDE.md`, and remaining subscription/quota limits — never blindly inherit the Runner's own model. Map complexity into three tiers (`mechanical` -> fast/`low`, `typical` -> fast/`medium`, `high-risk/architectural` -> strong/`high`) using live harness catalogs, project-documented model mappings, and availability checks per [harness routing](references/harnesses.md). Distribute work across the allowed harness pool from the prompt or `AGENTS.md`/`CLAUDE.md` (defaulting to the Runner's own harness when no pool is specified), and apply reactive failover whenever a harness or model tier hits rate limits or quota exhaustion. Launch Workers and Reviewers with auto-approve and maximum permissions paired with the mandatory prompt guardrails in [harness routing](references/harnesses.md#mandatory-prompt-guardrails).
- **Worker execution:** The Worker modifies only its assigned task worktree, stores ephemeral logs, screenshots, and verification evidence inside `<worktree>/.implement-tasks/<task-id>/`, reads `GLOSSARY.md`, relevant `docs/adr/` files, and `.agents/skills/tdd/SKILL.md` (when present) to build behavior red-before-green strictly at public module seams, runs relevant checks, and commits locally. For user-facing or visual changes, capture screenshots, clips, or rendered output when tooling is available. When the entire task is ready for review, the Worker sends a final `ready` report containing the task ID, implementation token, submitted SHA, summary, acceptance criteria status, test outcomes, verification gaps, and worktree-relative artifact paths. A Worker unable to proceed sends a `blocked` report. The Runner advances independent tasks and refreshes the **Status Pane** while monitoring Herdr (`hc wait`/`hc get`/`hc read` in GUI; `herdr agent get`/`herdr agent read` in TUI).
- **Review gate and peer-to-peer loop:** Start the **Review Gate** only after receiving the Worker's final `ready` report and verifying its implementation token, clean worktree, and matching `HEAD` SHA. Treat intermediate commits, progress messages, or a settled pane state (`idle`/`done` — especially for `agy` and `grok`) as work in progress until the completion line and SHA are verified. Evaluate the Review Gate against `git diff "$base_sha...$submitted_sha"` per [auto-merge and review rules](references/auto-merge-rules.md):
  - **Skip review (`--no-review` OR verified trivial mechanical diff):** Do not launch a Reviewer pane. Record `review_skipped: true` and `review_skip_reason` in the Run Record, evaluate `approval=auto|human` as Runner directly on `submitted_sha`, and proceed straight to PR publishing (in `pr` mode) or archiving and the Approval Gate.
  - **Run peer-to-peer review:** Split the Worker pane to the right (`herdr-app do pane.split` in GUI; `herdr pane split` in TUI) and start a fresh Reviewer (same or different harness) in the same tab and worktree. Give the Reviewer the pinned base SHA, submitted implementation SHA, task and spec, verification evidence, Worker's Herdr handle/name and pane ID, `<repo-root>/.agents/implement-tasks-auto-merge.md` (if present), and the two-axis review protocol (matching `.agents/skills/code-review/SKILL.md` when present): **Standards** (repo coding standards, ADRs, and Fowler smell baseline, separating hard violations from judgement calls) and **Spec** (acceptance criteria + linked spec completeness, accuracy, and scope creep), reported separately so passing one axis never masks a failure in the other. Let the Reviewer and Worker exchange findings, fixes, and reasoned disagreements directly through Herdr (`hc send` in GUI; `herdr agent prompt` in TUI), persisting state in `<worktree>/.implement-tasks/<task-id>/review-state.json`. Allow at most **5 correction rounds**, including re-review of the fifth response. Every Reviewer `pass` report must also include `approval=auto` or `approval=human` (with the exact reason when `human`) per [auto-merge rules](references/auto-merge-rules.md). If issues remain and a sixth round would be needed (or human judgment is required earlier), the Reviewer stops and reports `escalated` to the Runner.
- **Publish PR and verify CI (`pr` delivery mode):** After `verdict=pass` (or verified `ready` when review was skipped), the Runner sends `SHIP_PR` with `$ship_token` to the Worker, authorizing `git push -u origin HEAD:<task_branch>` and `gh pr create --base <primary_branch> --head <task_branch>` (formatting the PR body with `.agents/skills/pr/SKILL.md` when present and `GLOSSARY.md` vocabulary). The Runner watches `gh pr checks <pr-url> --watch`. If CI fails, the Runner feeds `gh run view --log-failed` back to the Worker in `<worktree_path>` to fix, re-verify locally, push `<task_branch>`, and (for non-trivial fixes when review ran) pass a delta check with the Reviewer within the 5-round cap.
- **Archive, evaluate Approval Gate, and act:** On `pass` (and green CI in `pr` mode), `escalated`, OR verified `ready` with `review_skipped: true`, always archive referenced artifacts (and `review-state.json` when review ran) from `<worktree>/.implement-tasks/<task-id>/` into `<git-common-dir>/implement-tasks/<task-id>/` and write `<git-common-dir>/implement-tasks/<task-id>/summary.md` **before** any merge or cleanup.
  - **Auto-merge eligible (verified `pass` or `ready` with `review_skipped: true`, `approval=auto` from both Runner and Reviewer when reviewed or Runner alone when review skipped, project rules satisfied, zero verification gaps, CI green in `pr` mode, and not `--handle`):** Follow [integration](references/integration.md) to merge (`--no-ff --no-commit` in `local` mode, or `gh pr merge` + `git pull --ff-only` in `pr` mode), commit `Backlog.md` `Done` (and push `<primary_branch>` in `pr` mode), automatically clean up the task's Herdr terminals, space/workspace, Git worktree, and merged branch, advance `base_sha` to the new primary `HEAD` (or `origin/<primary_branch>` in `pr` mode), reassess deferred tasks, and publish the PR/merge SHA, `Done` commit SHA, concise change/test summary, and clickable links to archived `summary.md` and screenshots/artifacts in the Runner's **Status Pane** (`status.md`). Never run `git push` automatically in `local` mode.
  - **Human approval required (`--handle`, OR `approval=human` / project require-approve match / verification gaps / unconfigured rules, OR `escalated`, OR merge/CI failure):** Do not merge or delete the worktree. Open the third/summary pane `summary-<task-id>` in the task tab (adaptive split from the Reviewer pane when review ran, or from the Worker pane when review was skipped, without stealing focus) displaying `summary.md` with a **Why approval is needed** section (and PR link / CI status in `pr` mode), leave the task **In Progress**, free the concurrency slot for other tasks, update the **Status Pane** (`awaiting approval` / `escalated` / `needs attention`), and notify the user explicitly in Runner chat with the task ID, reason, `summary-<task-id>` reference, and the required command (`approve <task-id>`).

## Integration rules

Read [approval and integration](references/integration.md) before performing any merge or worktree cleanup — both during automatic risk-gated integration and when the user explicitly authorizes integration via `approve <task-id>`, `approve all`, or synonym `merge <task-id>` (or requests manual cleanup / `git push`).

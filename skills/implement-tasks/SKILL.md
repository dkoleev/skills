# Implement Tasks

Use this skill explicitly from the primary Git checkout inside a **Herdr GUI** session (`HC_TERMINAL_ID`, via `herdr-app` + `hc`) or a **Herdr TUI** session (`HERDR_ENV=1`, via `herdr`) from any supported coding-agent harness pane. Move eligible tasks to **To Do** in `Backlog.md`, then invoke `implement-tasks` (with optional task IDs, harness pool hints, or subscription-limit preferences). A separate explicit instruction such as `merge TASK-12` authorizes integration, `Done` transition, and worktree/space cleanup for that task (unless you explicitly ask to keep the workspace open).

## Select and assign

1. Detect the Orchestration Backend:
   - **Herdr GUI (primary):** when `HC_TERMINAL_ID` is set, read `herdr-app --skill` and `hc --skill` and verify `herdr-app ls` and `hc ls --json`. Never fall back to `herdr` TUI commands inside Herdr GUI.
   - **Herdr TUI (fallback):** when `HC_TERMINAL_ID` is unset and `HERDR_ENV=1`, read `herdr --skill` (or the `herdr` skill) and confirm installed `herdr` commands.
   Identify the primary checkout (`git rev-parse --show-toplevel`), its current branch, and `<git-common-dir>`, ensuring `.implement-tasks/` is listed in `<git-common-dir>/info/exclude` without modifying the repository's tracked `.gitignore`. Follow [Herdr dispatch](references/herdr-dispatch.md) and [harness routing](references/harnesses.md).
2. Reconcile existing Run Records in `<git-common-dir>/implement-tasks/` first so in-flight `In Progress` runs are resumed by task ID and phase. Then query newly eligible tasks from the Task Source (`Backlog.md`) via `backlog task list --status "To Do" --ready --json` and compare against `backlog task list --status "To Do" --json` (without `--ready`) to detect blocked dependencies. Apply any explicit task-ID filter (an explicitly named `Backlog` task is eligible). Keep blocked dependencies, parent grouping tickets, tasks assigned to someone else, and owner-only tasks per `AGENTS.md`/`CLAUDE.md` (for example `project: owner`) out of the execution queue. Report skipped and deferred tasks with reasons. Keep tracker mutations isolated to the Runner so alternative Task Sources can be added later without changing the core loop. If no eligible or resumable tasks remain, finish without launching agents.
3. Inspect existing worktrees and saved Run Records in `<git-common-dir>/implement-tasks/` before dispatching, and resume existing runs by task ID and phase. Run up to **10 independent tasks** concurrently across implementation and review by default (worktrees awaiting user approval free a concurrency slot). Read project-specific conflict surfaces, exclusive local-resource serialization rules (for example, shared IDE/editor instances, databases, ports, or test hardware), and verification/artifact expectations from `AGENTS.md`, `CLAUDE.md`, and the launch prompt. Defer tasks likely to conflict with pending edits to shared files until those edits are integrated, and serialize checks that contend on an exclusive local resource. Reassess the queue as tasks finish.
4. When dispatching a `To Do` task for the first time:
   - Verify the task card file is clean and committed in the primary checkout (`git status --porcelain -- <card-path>`).
   - Update the task via `backlog task edit <task-id> --status "In Progress"` (and set assignee `-a <worker-name>` if unassigned, respecting any existing human assignment), then commit **only** that card file in the primary checkout (`git commit --only -m "<task-id>: In Progress" -- "<card-path>"`).
   - Pin `base_sha` to the resulting `HEAD`, create the task branch and linked worktree from `base_sha`, and launch the Worker in the new Herdr GUI space (`herdr-app do space.new`) or Herdr TUI workspace (`herdr worktree create`).
   - If worktree creation or Worker startup fails before prompt delivery, roll the card status back to `To Do` in the primary checkout and commit the rollback.
   - Keep all `Backlog.md` mutations with the Runner. Pass the Worker the task ID, acceptance criteria, relevant specification and absolute paths from the primary checkout (uncommitted tracker files are absent in a fresh worktree), applicable repo instructions and topic rules, and mandatory prompt guardrails.

## Implement, review, and summarize

- **Harness, model, and effort selection:** Select the harness, model, and reasoning effort separately for each Worker and Reviewer based on task complexity, card preferences in `AGENTS.md`/`CLAUDE.md`, and remaining subscription/quota limits — never blindly inherit the Runner's own model. Map complexity into three tiers (`mechanical` -> fast/`low`, `typical` -> fast/`medium`, `high-risk/architectural` -> strong/`high`) using live harness catalogs, project-documented model mappings, and availability checks per [harness routing](references/harnesses.md). Distribute work across the allowed harness pool from the prompt or `AGENTS.md`/`CLAUDE.md` (defaulting to the Runner's own harness when no pool is specified), and apply reactive failover whenever a harness or model tier hits rate limits or quota exhaustion. Launch Workers and Reviewers with auto-approve and maximum permissions paired with the mandatory prompt guardrails in [harness routing](references/harnesses.md#mandatory-prompt-guardrails).
- **Worker execution:** The Worker modifies only its assigned task worktree, stores ephemeral logs, screenshots, and verification evidence inside `<worktree>/.implement-tasks/<task-id>/`, runs relevant checks, and commits locally. For user-facing or visual changes, capture screenshots, clips, or rendered output when tooling is available. When the entire task is ready for review, the Worker sends a final `ready` report containing the task ID, implementation token, submitted SHA, summary, acceptance criteria status, test outcomes, verification gaps, and worktree-relative artifact paths. A Worker unable to proceed sends a `blocked` report. The Runner advances independent tasks while monitoring Herdr (`hc wait`/`hc get`/`hc read` in GUI; `herdr agent get`/`herdr agent read` in TUI).
- **Review gate and peer-to-peer loop:** Start review only after receiving the Worker's final `ready` report and verifying its implementation token, clean worktree, and matching `HEAD` SHA. Treat intermediate commits, progress messages, or a settled pane state (`idle`/`done` — especially for `agy` and `grok`) as work in progress until the completion line and SHA are verified. Split the Worker pane to the right (`herdr-app do pane.split` in GUI; `herdr pane split` in TUI) and start a fresh Reviewer (same or different harness) in the same tab and worktree. Give the Reviewer the pinned base SHA, submitted implementation SHA, task and spec, verification evidence, Worker's Herdr handle/name and pane ID, and review protocol. Let the Reviewer and Worker exchange findings, fixes, and reasoned disagreements directly through Herdr (`hc send` in GUI; `herdr agent prompt` in TUI), persisting state in `<worktree>/.implement-tasks/<task-id>/review-state.json`. Allow at most **5 correction rounds**, including re-review of the 5th response. If issues remain and a 6th round would be needed (or human judgment is required earlier), the Reviewer stops and reports `escalated` to the Runner.
- **Archive and Summary Pane:** On `pass` or `escalated`, archive referenced artifacts and `review-state.json` from `<worktree>/.implement-tasks/<task-id>/` into `<git-common-dir>/implement-tasks/<task-id>/`, and write `<git-common-dir>/implement-tasks/<task-id>/summary.md` with the task ID, verdict, branch, `base..reviewed SHA`, harnesses/models used, summary of changes and touched files, test outcomes and verification gaps, review rounds (or unresolved escalation details), and clickable absolute/`file://` links to archived screenshots and artifacts. Open a third pane named `summary-<task-id>` beside the Worker and Reviewer in the task tab (adaptive split from the Reviewer pane with `--no-focus` / without stealing focus) and display `summary.md` there. Leave the task **In Progress** and keep the worktree and panes open for user review.

## Integrate after approval

Read [approval and integration](references/integration.md) only when the user explicitly authorizes merging or closing named tasks or worktrees. A new invocation of `implement-tasks` dispatches or resumes queued work. Approval applies strictly to the reported, reviewed SHA of the named task: it authorizes sequential merge, combined verification, updating the `Backlog.md` card to `Done` (committed separately from the code merge), and automatic cleanup of the task's Herdr terminals, space/workspace, Git worktree, and merged branch — unless the user explicitly asks to keep them open. `git push` always requires separate explicit authorization.

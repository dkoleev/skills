# Implement Tasks

Use this skill explicitly from the primary Git checkout inside a **Herdr GUI** session (`HC_TERMINAL_ID`, via `herdr-app` + `hc`) or a **Herdr TUI** session (`HERDR_ENV=1`, via `herdr`) from any supported coding-agent harness pane. Move eligible tasks to **To Do** in `Backlog.md`, then invoke `implement-tasks` (with optional task IDs, harness pool hints, subscription-limit preferences, or `--handle`).

Two integration modes are supported:
- **Default (risk-gated auto-merge) mode:** Routine, verified `pass` changes that satisfy the project's `.agents/implement-tasks-auto-merge.md` rules and carry `approval=auto` from both Runner and Reviewer are archived, sequentially merged locally (`--no-ff --no-commit` + combined verification), committed as `Done` in `Backlog.md`, and automatically cleaned up (Herdr terminals, space/workspace, Git worktree, merged branch), advancing `base_sha` and updating the Runner's **Status Pane** with links to archived evidence. Complex, risky, sensitive-path, or unverified changes (or runs with unconfigured rules) pause and wait for your explicit `approve <task-id>`. `git push` always requires separate explicit authorization.
- **Manual approval mode (`--handle`):** Disables auto-merge for every task. All passing tasks remain **In Progress** with their worktree, Worker, Reviewer, and task-tab **Summary Pane** open until you explicitly authorize `approve <task-id>` (or synonym `merge <task-id>`).

## Select and assign

1. Detect the Orchestration Backend:
   - **Herdr GUI (primary):** when `HC_TERMINAL_ID` is set, read `herdr-app --skill` and `hc --skill` and verify `herdr-app ls` and `hc ls --json`. Never fall back to `herdr` TUI commands inside Herdr GUI.
   - **Herdr TUI (fallback):** when `HC_TERMINAL_ID` is unset and `HERDR_ENV=1`, read `herdr --skill` (or the `herdr` skill) and confirm installed `herdr` commands.
   Identify the primary checkout (`git rev-parse --show-toplevel`), its current branch, and `<git-common-dir>`, ensuring `.implement-tasks/` is listed in `<git-common-dir>/info/exclude` without modifying the repository's tracked `.gitignore`. Follow [Herdr dispatch](references/herdr-dispatch.md), [harness routing](references/harnesses.md), and [auto-merge rules](references/auto-merge-rules.md).
2. Check project auto-merge configuration (when not running with `--handle`):
   - Inspect `<repo-root>/.agents/implement-tasks-auto-merge.md` (or a custom path declared in `AGENTS.md`/`CLAUDE.md`) per [auto-merge rules](references/auto-merge-rules.md).
   - If the file is missing or unfilled, **warn the user** and ask whether to: (a) let the Runner analyze the project and draft `.agents/implement-tasks-auto-merge.md` for confirmation, (b) record rules dictated by the user, or (c) continue this run safely requiring `approve <task-id>` for all tasks (never silently auto-merge without configured rules).
3. Reconcile existing Run Records in `<git-common-dir>/implement-tasks/` first so in-flight `In Progress` runs are resumed by task ID and phase. Then query newly eligible tasks from the Task Source (`Backlog.md`) via `backlog task list --status "To Do" --ready --json` and compare against `backlog task list --status "To Do" --json` (without `--ready`) to detect blocked dependencies. Apply any explicit task-ID filter (an explicitly named `Backlog` task is eligible). Keep blocked dependencies, parent grouping tickets, tasks assigned to someone else, and owner-only tasks per `AGENTS.md`/`CLAUDE.md` (for example `project: owner`) out of the execution queue. Report skipped and deferred tasks with reasons. Keep tracker mutations isolated to the Runner so alternative Task Sources can be added later without changing the core loop. If no eligible or resumable tasks remain, finish without launching agents or panes.
4. Once at least one eligible or resumable task is identified, open (or reuse) the Runner's **Status Pane** (`implement-tasks-status`) beside the Runner pane and render `<git-common-dir>/implement-tasks/status.md` per [Herdr dispatch](references/herdr-dispatch.md#runner-status-pane-statusmd); refresh it on every queue or task transition. Run up to **10 independent tasks** concurrently across implementation and review by default (worktrees awaiting `approve` free a concurrency slot). Read project-specific conflict surfaces, exclusive local-resource serialization rules (for example, shared IDE/editor instances, databases, ports, or test hardware), and verification/artifact expectations from `AGENTS.md`, `CLAUDE.md`, and the launch prompt. Defer tasks likely to conflict with pending edits to shared files until those edits are integrated, and serialize checks that contend on an exclusive local resource. Reassess the queue as tasks finish or merge.
5. When dispatching a `To Do` task for the first time:
   - Verify the task card file is clean and committed in the primary checkout (`git status --porcelain -- <card-path>`).
   - Update the task via `backlog task edit <task-id> --status "In Progress"` (and set assignee `-a <worker-name>` if unassigned, respecting any existing human assignment), then commit **only** that card file in the primary checkout (`git commit --only -m "<task-id>: In Progress" -- "<card-path>"`).
   - Pin `base_sha` to the resulting `HEAD`, create the task branch and linked worktree from `base_sha`, and launch the Worker in the new Herdr GUI space (`herdr-app do space.new`) or Herdr TUI workspace (`herdr worktree create`).
   - If worktree creation or Worker startup fails before prompt delivery, roll the card status back to `To Do` in the primary checkout and commit the rollback.
   - Keep all `Backlog.md` mutations with the Runner. Pass the Worker the task ID, acceptance criteria, relevant specification and absolute paths from the primary checkout (uncommitted tracker files are absent in a fresh worktree), applicable repo instructions and topic rules, and mandatory prompt guardrails.

## Implement, review, summarize, and integrate

- **Harness, model, and effort selection:** Select the harness, model, and reasoning effort separately for each Worker and Reviewer based on task complexity, card preferences in `AGENTS.md`/`CLAUDE.md`, and remaining subscription/quota limits — never blindly inherit the Runner's own model. Map complexity into three tiers (`mechanical` -> fast/`low`, `typical` -> fast/`medium`, `high-risk/architectural` -> strong/`high`) using live harness catalogs, project-documented model mappings, and availability checks per [harness routing](references/harnesses.md). Distribute work across the allowed harness pool from the prompt or `AGENTS.md`/`CLAUDE.md` (defaulting to the Runner's own harness when no pool is specified), and apply reactive failover whenever a harness or model tier hits rate limits or quota exhaustion. Launch Workers and Reviewers with auto-approve and maximum permissions paired with the mandatory prompt guardrails in [harness routing](references/harnesses.md#mandatory-prompt-guardrails).
- **Worker execution:** The Worker modifies only its assigned task worktree, stores ephemeral logs, screenshots, and verification evidence inside `<worktree>/.implement-tasks/<task-id>/`, runs relevant checks, and commits locally. For user-facing or visual changes, capture screenshots, clips, or rendered output when tooling is available. When the entire task is ready for review, the Worker sends a final `ready` report containing the task ID, implementation token, submitted SHA, summary, acceptance criteria status, test outcomes, verification gaps, and worktree-relative artifact paths. A Worker unable to proceed sends a `blocked` report. The Runner advances independent tasks and refreshes the **Status Pane** while monitoring Herdr (`hc wait`/`hc get`/`hc read` in GUI; `herdr agent get`/`herdr agent read` in TUI).
- **Review gate and peer-to-peer loop:** Start review only after receiving the Worker's final `ready` report and verifying its implementation token, clean worktree, and matching `HEAD` SHA. Treat intermediate commits, progress messages, or a settled pane state (`idle`/`done` — especially for `agy` and `grok`) as work in progress until the completion line and SHA are verified. Split the Worker pane to the right (`herdr-app do pane.split` in GUI; `herdr pane split` in TUI) and start a fresh Reviewer (same or different harness) in the same tab and worktree. Give the Reviewer the pinned base SHA, submitted implementation SHA, task and spec, verification evidence, Worker's Herdr handle/name and pane ID, `<repo-root>/.agents/implement-tasks-auto-merge.md` (if present), and the review protocol. Let the Reviewer and Worker exchange findings, fixes, and reasoned disagreements directly through Herdr (`hc send` in GUI; `herdr agent prompt` in TUI), persisting state in `<worktree>/.implement-tasks/<task-id>/review-state.json`. Allow at most **5 correction rounds**, including re-review of the fifth response. Every Reviewer `pass` report must also include `approval=auto` or `approval=human` (with the exact reason when `human`) per [auto-merge rules](references/auto-merge-rules.md). If issues remain and a sixth round would be needed (or human judgment is required earlier), the Reviewer stops and reports `escalated` to the Runner.
- **Archive, evaluate Approval Gate, and act:** On `pass` or `escalated`, always archive referenced artifacts and `review-state.json` from `<worktree>/.implement-tasks/<task-id>/` into `<git-common-dir>/implement-tasks/<task-id>/` and write `<git-common-dir>/implement-tasks/<task-id>/summary.md` **before** any merge or cleanup.
  - **Auto-merge eligible (`pass`, `approval=auto` from both Runner and Reviewer, project rules satisfied, and not `--handle`):** Follow [integration](references/integration.md) to sequentially merge locally (`--no-ff --no-commit` + combined verification), commit `Backlog.md` `Done`, automatically clean up the task's Herdr terminals, space/workspace, Git worktree, and merged branch, advance `base_sha` to the new primary `HEAD`, reassess deferred tasks, and publish the merge SHA, `Done` commit SHA, concise change/test summary, and clickable links to archived `summary.md` and screenshots/artifacts in the Runner's **Status Pane** (`status.md`). Never run `git push` automatically.
  - **Human approval required (`--handle`, OR `approval=human` / project require-approve match / verification gaps / unconfigured rules, OR `escalated`, OR auto-merge failure):** Do not merge or delete the worktree. Open the third pane `summary-<task-id>` beside the Worker and Reviewer in the task tab (adaptive split from the Reviewer pane without stealing focus) displaying `summary.md` with a **Why approval is needed** section, leave the task **In Progress**, free the concurrency slot for other tasks, update the **Status Pane** (`awaiting approval` / `escalated` / `needs attention`), and notify the user explicitly in Runner chat with the task ID, reason, `summary-<task-id>` reference, and the required command (`approve <task-id>`).

## Integration rules

Read [approval and integration](references/integration.md) before performing any merge or worktree cleanup — both during automatic risk-gated integration and when the user explicitly authorizes integration via `approve <task-id>`, `approve all`, or synonym `merge <task-id>` (or requests manual cleanup / `git push`).

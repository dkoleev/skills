# Implement Tasks

Use this skill explicitly from the primary Git checkout inside a Herdr GUI session (`HERDR_ENV=1`) from any supported coding-agent harness pane. Move eligible tasks to **In Progress** in `Backlog.md`, then invoke `implement-tasks` (with optional task IDs, harness pool hints, or subscription-limit preferences). A separate explicit instruction such as `merge TASK-12 and close its worktree` authorizes integration for that task only.

## Select and assign

1. Verify `HERDR_ENV=1`, read the `herdr` skill (or `herdr --skill`) and `backlog instructions task-execution`, and confirm the installed Herdr commands. Identify the primary checkout, its current branch, and pin its `HEAD` as the base SHA for newly dispatched work. Ensure `.implement-tasks/` is listed in `<git-common-dir>/info/exclude` without modifying the repository's tracked `.gitignore`. Follow [Herdr dispatch](references/herdr-dispatch.md) and [harness routing](references/harnesses.md).
2. Read the Task Source (`Backlog.md`) via `backlog task list --status "In Progress" --ready --json` and compare against the list without `--ready` to detect blocked dependencies. Apply any explicit task-ID filter. Keep blocked dependencies, tasks assigned to someone else, and parent tickets that only group child work out of the execution queue. Report skipped and deferred tasks with reasons. Keep tracker mutations isolated to the Runner so alternative Task Sources can be added later without changing the core loop. If no eligible tasks remain, finish without launching agents.
3. Inspect existing worktrees and saved Run Records in `<git-common-dir>/implement-tasks/` before dispatching, and resume existing runs by task ID and phase. Run up to **10 independent tasks** concurrently across implementation and review by default (worktrees awaiting user approval free a concurrency slot). Read project-specific conflict surfaces, exclusive local-resource serialization rules (for example, shared IDE/editor instances, databases, ports, or test hardware), and verification/artifact expectations from `AGENTS.md`, `CLAUDE.md`, and the launch prompt. Defer tasks likely to conflict with pending edits to shared files until those edits are integrated, and serialize checks that contend on an exclusive local resource. Reassess the queue as tasks finish.
4. When dispatching a task for the first time, create its branch and linked worktree with `herdr worktree create` from the pinned base SHA. Launch the Worker in the root pane of the workspace returned by Herdr. In the primary `Backlog.md`, set the task assignee to the Worker's Herdr name via the CLI (respecting any existing human assignment) and record the researched plan. Keep all `Backlog.md` mutations with the Runner. Pass the Worker the task ID, acceptance criteria, relevant specification and absolute paths from the primary checkout (uncommitted tracker files are absent in a fresh worktree), applicable repo instructions, and mandatory prompt guardrails.

## Implement, review, and summarize

- **Harness, model, and effort selection:** Select the harness, model, and reasoning effort separately for each Worker and Reviewer based on task complexity and remaining subscription/quota limits — never blindly inherit the Runner's own model. Map complexity into three tiers (`mechanical` -> fast/`low`, `typical` -> fast/`medium`, `high-risk/architectural` -> strong/`high`) using live harness catalogs and availability checks per [harness routing](references/harnesses.md). Distribute work across the allowed harness pool from the prompt or `AGENTS.md`/`CLAUDE.md` (defaulting to the Runner's own harness when no pool is specified), and apply reactive failover whenever a harness or model tier hits rate limits or quota exhaustion. Launch Workers and Reviewers with auto-approve and maximum permissions paired with the mandatory prompt guardrails in [harness routing](references/harnesses.md#mandatory-prompt-guardrails).
- **Worker execution:** The Worker modifies only its assigned task worktree, stores ephemeral logs, screenshots, and verification evidence inside `<worktree>/.implement-tasks/<task-id>/`, runs relevant checks, and commits locally. For user-facing or visual changes, capture screenshots, clips, or rendered output when tooling is available. When the entire task is ready for review, the Worker sends a final `ready` report containing the task ID, implementation token, submitted SHA, summary, acceptance criteria status, test outcomes, verification gaps, and worktree-relative artifact paths. A Worker unable to proceed sends a `blocked` report. The Runner advances independent tasks while monitoring Herdr.
- **Review gate and peer-to-peer loop:** Start review only after receiving the Worker's final `ready` report and verifying its implementation token, clean worktree, and matching `HEAD` SHA. Treat intermediate commits, progress messages, or a settled pane state (`idle`/`done` — especially for `agy` and `grok`) as work in progress until the completion line and SHA are verified. Split the Worker pane to the right and start a fresh Reviewer (same or different harness) in the same tab and worktree. Give the Reviewer the pinned base SHA, submitted implementation SHA, task and spec, verification evidence, Worker's Herdr name and pane ID, and review protocol. Let the Reviewer and Worker exchange findings, fixes, and reasoned disagreements directly through Herdr (`herdr agent prompt`), persisting state in `<worktree>/.implement-tasks/<task-id>/review-state.json`. Allow at most **5 correction rounds**, including re-review of the fifth response. If issues remain and a sixth round would be needed (or human judgment is required earlier), the Reviewer stops and reports `escalated` to the Runner.
- **Archive and Summary Pane:** On `pass` or `escalated`, archive referenced artifacts and `review-state.json` from `<worktree>/.implement-tasks/<task-id>/` into `<git-common-dir>/implement-tasks/<task-id>/`, and write `<git-common-dir>/implement-tasks/<task-id>/summary.md` with the task ID, verdict, branch, `base..reviewed SHA`, harnesses/models used, summary of changes and touched files, test outcomes and verification gaps, review rounds (or unresolved escalation details), and clickable absolute/`file://` links to archived screenshots and artifacts. Open a third pane named `summary-<task-id>` beside the Worker and Reviewer in the task tab (adaptive split from the Reviewer pane with `--no-focus`) and display `summary.md` there. Leave the task **In Progress** and keep the worktree and panes open for user review.

## Integrate after approval

Read [approval and integration](references/integration.md) only when the user explicitly authorizes merging or closing named tasks or worktrees. A new invocation of `implement-tasks` dispatches or resumes queued work. Approval applies strictly to the reported, reviewed SHA of the named task and only to the actions the user authorizes.
